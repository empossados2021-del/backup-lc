# Spec E2.3 — Agendamento configurável pela interface

| Campo | Valor |
| --- | --- |
| Status | **Proposta** — aguardando aprovação |
| Base | PRD v2.0 (F-05), Spec E4 |
| Data | 2026-11-06 |

## 1. Objetivo

Permitir que o administrador configure o horário da coleta diária automática
diretamente pela interface web, sem precisar reiniciar o sistema ou editar variáveis de ambiente.

## 2. Escopo

### 2.1 Tabela `app_settings`

Nova tabela chave-valor no banco para guardar configurações persistentes:

| Coluna | Tipo | Descrição |
| --- | --- | --- |
| `key` | TEXT PK | Nome da configuração |
| `value` | TEXT | Valor |
| `updated_at` | DATETIME | Última alteração |

Chave usada nesta etapa: `schedule_cron` (padrão `"0 2 * * *"`).

### 2.2 Página `/settings` (admin)

Nova entrada no menu lateral em **Administração → Configurações**.

Formulário com dois campos simples — sem cron bruto para o usuário:

| Campo | Controle | Validação |
| --- | --- | --- |
| **Hora** | `<select>` 0–23 | obrigatório |
| **Minuto** | `<select>` 0, 15, 30, 45 | obrigatório |

Converte internamente para `"M H * * *"` antes de salvar.

Exibe também:
- Expressão cron atual (ex.: `0 2 * * *`)
- Próxima execução prevista (calculada no servidor)
- Botão **Salvar**

### 2.3 Atualização dinâmica do agendador

Ao salvar, o `APScheduler` tem o job reescalonado imediatamente via
`scheduler.reschedule_job()` — sem reiniciar o serviço.

A instância do scheduler é exposta em `request.app.state.scheduler`.

### 2.4 Inicialização

Na inicialização do app, lê `schedule_cron` do banco (se existir) em vez
do valor padrão da env `BLC_SCHEDULE_CRON`. Se a chave não existir no
banco, usa o padrão e não cria registro até a primeira edição.

## 3. O que não entra nesta etapa

- Agendamentos por dispositivo individual.
- Dias da semana configuráveis (futuro).
- Múltiplas janelas de coleta por dia (futuro).

## 4. Testes esperados

- Salvar novo horário persiste no banco e reescalona o job.
- `/settings` só acessível para admin.
- Horário inválido (hora > 23) retorna erro de validação.
- Na inicialização, cron do banco tem prioridade sobre o padrão.
- Próxima execução exibida é coerente com o cron salvo.

## 5. Critérios de aceite

- [ ] Admin consegue mudar o horário da coleta pela UI sem reiniciar.
- [ ] Mudança persiste após reinício do container.
- [ ] Próxima execução reflete o novo horário imediatamente.
- [ ] Todos os testes existentes continuam passando.
